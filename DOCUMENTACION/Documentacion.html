Bienvenido a SecureTenis

Documentación técnica completa del proyecto de fin de grado · 2º DAW · 2025–2026

¿Qué es SecureTenis? Una plataforma de comercio electrónico de zapatillas deportivas con panel de administración completo, autenticación segura con JWT, control de acceso por roles y auditoría de eventos en tiempo real.

Descripción del proyecto

SecureTenis es una tienda online construida como Trabajo de Fin de Grado del ciclo superior de Desarrollo de Aplicaciones Web. Integra un frontend reactivo en Vue 3 con un backend REST en Express sobre TypeScript, base de datos MariaDB gestionada mediante Prisma ORM y toda la infraestructura orquestada con Docker Compose.

El proyecto demuestra cómo implementar de forma profesional conceptos avanzados como autenticación JWT, protección contra ataques de fuerza bruta, registro de auditoría completo y un panel de administración con estadísticas y gráficas.

Funcionalidades principales

Tienda

Catálogo con filtrado por categoría, carrito persistente (anónimo + autenticado con fusión automática al hacer login), gestión de cantidades, proceso de compra con reducción de stock y historial de pedidos.

Autenticación y seguridad

Registro e inicio de sesión con JWT, hash de contraseñas con bcrypt, auto-bloqueo tras 5 intentos fallidos en 10 minutos, bloqueo manual de usuarios e IPs, correo de bienvenida automático.

Panel de administración

Gestión de usuarios, productos y categorías. Visualización de estadísticas con Chart.js, registro de auditoría con filtros avanzados, gestión de bloqueos activos y exportación de logs en CSV/PDF.

Control de roles

Tres roles diferenciados: CLIENT (usuario de tienda), ADMIN (acceso total al panel) y ANALYST (solo lectura de métricas y auditoría). Protección aplicada en frontend y backend.

Stack tecnológico

Todas las dependencias, frameworks y herramientas utilizadas en el proyecto.

Frontend

Vue 3.5 Vite 7.x Pinia 3.x Vue Router 5.x TypeScript 5.9 Bootstrap 5.3 Chart.js 4.x

Vue 3 + Composition API

Framework reactivo principal. Toda la lógica de componentes usa script setup y la Composition API, lo que permite una mejor organización del código y reutilización de lógica entre vistas.

Vite

Bundler de nueva generación. Ofrece arranque instantáneo en desarrollo y compilaciones optimizadas para producción con code splitting automático.

Pinia

Gestor de estado global oficial para Vue 3. Se usa para compartir el estado de autenticación y el carrito entre todas las vistas sin necesidad de pasar props manualmente.

Vue Router

Manejo de navegación SPA con rutas anidadas. Implementa navigation guards para proteger rutas según rol y estado de autenticación.

Backend

Node.js 20+ Express 5.x TypeScript 5.9 Prisma ORM 6.x Zod 4.x bcryptjs 3.x jsonwebtoken 9.x Nodemailer 8.x

Express 5

Framework HTTP minimalista y maduro. La versión 5 mejora el manejo de promesas en los handlers, evitando tener que capturar errores manualmente en cada controlador asíncrono.

Prisma ORM

ORM moderno con tipado estático completo. Define el esquema en un único archivo schema.prisma y genera un cliente tipado automáticamente. Gestiona las migraciones de base de datos de forma versionada.

Zod

Librería de validación con inferencia de tipos TypeScript. Se usa para validar los datos de entrada en los endpoints de registro y login antes de que lleguen al controlador.

bcryptjs + JWT

Combinación estándar para autenticación segura. bcryptjs aplica hash irreversible a las contraseñas antes de guardarlas. jsonwebtoken genera tokens firmados que identifican al usuario en cada petición.

Infraestructura y base de datos

Docker Compose

Orquesta los contenedores del backend y MariaDB en una red compartida. Un solo comando levanta todo el entorno.

MariaDB 11

Base de datos relacional compatible con MySQL. Almacena usuarios, productos, pedidos, logs, carrito y bloqueos.

Prisma Migrate

Sistema de migraciones versionado. Cada cambio en el esquema genera un archivo SQL histórico que puede reproducirse en cualquier entorno.

Arquitectura del sistema

Cómo se comunican las capas del proyecto y qué responsabilidad tiene cada una.

Diagrama de capas

Flujo de una petición típica

1
El usuario realiza una acción en el frontend (p.ej. añadir al carrito). El apiClient construye la petición con el JWT y el session-id y la envía al backend.
2
checkBlock comprueba si la IP o el usuario están bloqueados. Si lo están, devuelve 403 inmediatamente sin procesar nada más.
3
El router de Express encuentra la ruta correspondiente y aplica los middlewares de autenticación (authenticate) y autorización (authorize) si la ruta los requiere.
4
El middleware de validación Zod comprueba el cuerpo de la petición contra el esquema definido. Si hay errores, responde con 400 y los mensajes de error.
5
El controlador recibe la petición ya validada y autenticada, llama al servicio correspondiente y devuelve la respuesta JSON al cliente.
6
Si en cualquier paso ocurre un error no controlado, el errorHandler global lo captura y devuelve una respuesta 500 sin exponer detalles en producción.

Backend — Punto de entrada

Los dos archivos que arrancan y configuran la aplicación Express.

backend/server.ts TS ▶

Punto de entrada absoluto del servidor. Se encarga de tres cosas: cargar las variables de entorno con dotenv, arrancar el servidor Express en el puerto configurado (por defecto 3000), y verificar que la conexión a la base de datos es correcta al inicio. Esta última comprobación usa una consulta SELECT 1 y registra el resultado como un log DEBUG en la base de datos, de forma que si la BD no está disponible queda constancia del fallo.

backend/src/app.ts TS ▶

Configura la aplicación Express con todos sus middlewares y rutas. El orden de registro es importante y deliberado:

1. Middlewares globales: CORS para permitir peticiones del frontend, express.json() para parsear el body, y Morgan para logging de peticiones HTTP en consola.

2. checkBlock: Se aplica ANTES que todas las rutas. Cualquier petición de una IP o usuario bloqueado termina aquí con un 403.

3. Rutas: Cada grupo de rutas está montado en su prefijo /api/....

4. Manejadores de error: Al final del todo. El notFoundHandler captura cualquier ruta no definida y el errorHandler captura excepciones no controladas de cualquier ruta anterior.

Backend — Middlewares

Capas de procesamiento que interceptan las peticiones antes de que lleguen a los controladores.

backend/src/middlewares/authMiddleware.ts TS ▶

Contiene tres funciones de control de acceso:


authenticate — Verifica que la petición incluya un token JWT válido en la cabecera Authorization: Bearer <token>. Si no hay token o es inválido/expirado, rechaza con 401 y genera un log de advertencia. Si el token es válido, añade los datos del usuario a req.user para que los controladores puedan usarlos.


optionalAuthenticate — Igual que authenticate, pero si no hay token simplemente continúa sin asignar usuario. Se usa en las rutas del carrito, que funcionan tanto para usuarios anónimos como autenticados.


authorize(...roles) — Factory que devuelve un middleware de autorización para los roles indicados. Comprueba que el usuario autenticado (req.user.role) tenga uno de los roles permitidos. Si no, devuelve 403 y registra el intento de acceso no autorizado.

backend/src/middlewares/checkBlock.ts TS ▶

Middleware global de bloqueo. Se ejecuta en cada petición antes de que llegue a cualquier ruta. Extrae la IP del cliente (usando getClientIp), el ID de usuario del token JWT (si existe) y el email del cuerpo de la petición. Luego consulta la base de datos para comprobar si alguno de esos identificadores tiene un bloqueo activo. Si está bloqueado, devuelve 403 con el motivo del bloqueo. Este mecanismo protege el sistema incluso si el atacante cambia de credenciales pero mantiene la misma IP.

backend/src/middlewares/errorMiddleware.ts TS ▶

Manejo centralizado de errores. Expone dos handlers registrados al final de la cadena de middlewares en app.ts:

notFoundHandler — Captura cualquier petición a una ruta que no exista y devuelve un 404 con el método y la URL solicitada.

errorHandler — Captura cualquier excepción no controlada que haya pasado hacia Express. En entorno de desarrollo expone el mensaje de error para facilitar el debugging; en producción devuelve únicamente el mensaje genérico para no filtrar información sensible.

backend/src/middlewares/validateMiddleware.ts TS ▶

Middleware de validación genérico que acepta un esquema Zod y devuelve un middleware de Express. Valida req.body contra el esquema. Si la validación falla, responde con 400 y un array con todos los mensajes de error. Si es válida, reemplaza req.body con el dato transformado por Zod (los esquemas Zod pueden transformar datos, como forzar el rol a 'cliente' en el registro).

Backend — Controladores

Los controladores orquestan la lógica: reciben la petición validada, llaman al servicio y devuelven la respuesta JSON.

backend/src/controllers/authController.ts TS ▶

Gestiona el registro, login y consulta del perfil. La lógica de seguridad más relevante reside aquí:


Registro (POST /api/auth/register): Llama a authService.register, fusiona el carrito de sesión con el del nuevo usuario (si existe un x-session-id), dispara el envío del correo de bienvenida de forma asíncrona (no bloquea la respuesta aunque falle el SMTP) y registra un log INFO.


Login (POST /api/auth/login): Además del proceso normal de autenticación, implementa un sistema de auto-bloqueo en memoria. Mantiene un Map con los intentos fallidos por email: si en 10 minutos acumula 5 fallos, llama a blockService.createAutoBlock para bloquear ese email durante 15 minutos y limpia el contador.

backend/src/controllers/productController.ts TS ▶

CRUD de productos. Los métodos GET son públicos. Los métodos POST, PUT y DELETE están protegidos en las rutas y solo son accesibles para administradores. Delega toda la interacción con la base de datos en productService.

backend/src/controllers/cartController.ts TS ▶

Gestiona las operaciones del carrito. Lee el x-session-id de la cabecera de la petición para identificar la sesión y lo pasa al servicio junto con el ID de usuario (si existe). Soporta añadir, actualizar cantidad, eliminar items y vaciar el carrito.

backend/src/controllers/orderController.ts TS ▶

Gestiona los pedidos del usuario. Al crear un pedido, el servicio obtiene todos los items del carrito, calcula el total, crea el pedido con sus items y reduce el stock de cada producto. También expone un endpoint especial para generar una factura en PDF que acepta el token como parámetro de query en lugar de cabecera (ya que se abre en una nueva pestaña del navegador).

backend/src/controllers/admin/ TS ▶

Cuatro controladores exclusivos del panel de administración:


userController — CRUD de usuarios. Solo para administradores. Permite listar usuarios, crear nuevos con rol asignado, cambiar el rol de un usuario existente y eliminar cuentas.


logController — Consulta el registro de auditoría. Soporta filtros por nivel, módulo, texto y rango de fechas con paginación. También genera exportaciones en CSV (usando array join) y PDF (usando la librería pdfkit).


statsController — Proxy delgado que llama a las funciones de statsService y devuelve las estadísticas de autenticación y del sistema directamente.


blockController — Gestión de bloqueos activos. Permite listar todos los bloqueos no expirados, crear bloqueos manuales por IP o email con duración opcional, y eliminar (desbloquear) por ID.

Backend — Servicios

La capa de lógica de negocio. Los servicios contienen toda la interacción con Prisma y las reglas del dominio.

backend/src/services/authService.ts TS ▶

Núcleo de la autenticación. Gestiona cuatro operaciones: findByEmail (búsqueda con mapeo de roles), findById (para /me, devuelve datos públicos sin contraseña), register (comprueba que el email no exista, hashea la contraseña con bcrypt usando los salt rounds de la variable de entorno y genera el JWT) y login (verifica la contraseña con bcrypt.compare y genera el token).


Contiene un mapa de traducción de roles entre el frontend ('admin'/'cliente'/'analista') y la base de datos ('ADMIN'/'CLIENT'/'ANALYST'), que se aplica en todos los mapeos.

backend/src/services/admin/blockService.ts TS ▶

Gestiona los bloqueos de acceso. La función más crítica es isBlocked: recibe la IP, el userId y el email, y busca en la base de datos si alguno de esos identificadores tiene un bloqueo activo (que no haya expirado). Devuelve { blocked: true, reason } si se encuentra alguno.


createAutoBlock registra un bloqueo temporal en la base de datos cuando el controlador de auth detecta que un email ha acumulado demasiados intentos fallidos.

backend/src/services/admin/statsService.ts TS ▶

Genera las estadísticas del panel de administración a partir de los datos reales de la base de datos:


getAuthStats — Cuenta logins exitosos y fallidos en los últimos 30 días, usuarios únicos que han hecho login hoy, y construye los datos para la gráfica de Chart.js (logins vs fallidos por día en los últimos 7 días).


getSystemStats — Devuelve conteos de todas las tablas principales, el número total de tablas en la base de datos (con una raw query a information_schema), la latencia de la base de datos medida en la propia llamada y la distribución de logs por nivel y por módulo.

backend/src/services/mailService.ts TS ▶

Gestiona el envío de correos electrónicos con Nodemailer. Si las variables de entorno SMTP_USER y SMTP_PASS no están configuradas, simula el envío mostrando un log en consola (modo seguro para desarrollo). Si están presentes, crea un transportador SMTP real y envía un correo HTML de bienvenida estilizado con el nombre del usuario y un enlace a la tienda.

backend/src/services/cartService.ts TS ▶

Lógica del carrito de compras. La función más relevante es mergeSessionCartIntoUser: cuando un usuario anónimo hace login o se registra, esta función toma todos los items de su carrito de sesión y los fusiona con el carrito del usuario. Si un producto ya existe en ambos, suma las cantidades; si no, transfiere el item. Al terminar, elimina todos los registros de la sesión anónima.

backend/src/services/admin/logService.ts TS ▶

Servicio de auditoría. Expone la función createLog que es llamada desde múltiples puntos de la aplicación (authController, authMiddleware, blockService) para registrar eventos. Gestiona también la consulta paginada de logs con filtros por nivel, módulo, texto libre y rango de fechas, y la generación de los archivos de exportación.

Backend — Validadores

Esquemas Zod que validan y transforman los datos de entrada antes de que lleguen a los controladores.

backend/src/validators/authValidator.ts TS ▶

Define dos esquemas de validación:


registerSchema — Valida nombre (2-100 caracteres), email (formato HTML5) y contraseña (6-128 caracteres). Aplica una transformación que fuerza el campo role a 'cliente' independientemente de lo que envíe el cliente, evitando que alguien se auto-asigne el rol de administrador en el registro público.


loginSchema — Valida únicamente email y contraseña con presencia obligatoria. Sin restricciones de longitud mínima en la contraseña para no limitar casos de uso.

Seguridad por diseño: La transformación del rol en registerSchema es una medida de seguridad importante. Aunque la API devuelva un error si se envía un rol no válido, la transformación garantiza que incluso si Zod lo dejara pasar, el rol siempre será 'cliente'. El rol solo puede ser cambiado desde el panel de administración.

Backend — Configuración

Archivos de configuración, utilidades y variables de entorno.

backend/src/config/jwt.ts TS ▶

Centraliza la configuración de JWT. Lee JWT_SECRET y JWT_EXPIRES_IN de las variables de entorno. Si no están definidas, usa valores por defecto (no recomendado en producción). Al estar en un único archivo, cambiar la clave o la expiración solo requiere modificar este lugar.

backend/src/config/prisma.ts TS ▶

Instancia singleton del cliente Prisma. Exporta un único objeto prisma que todos los servicios importan. Usar un singleton evita crear múltiples conexiones a la base de datos, lo que degradaría el rendimiento.

backend/src/utils/getClientIp.ts TS ▶

Utilidad para extraer la IP real del cliente. En entornos con proxy o Docker, la petición llega con la cabecera x-forwarded-for. Esta función la lee primero, tomando solo la primera IP si hay varias. También normaliza las direcciones IPv4-mapped en IPv6 (::ffff:1.2.3.4) a su forma IPv4 pura (1.2.3.4) para garantizar que los bloqueos por IP funcionen correctamente.

backend/src/types/index.ts TS ▶

Repositorio centralizado de tipos TypeScript del backend. Define las interfaces de todos los modelos de dominio (User, Product, CartItem, Order, etc.), los tipos de datos especiales (UserRole, LogLevel, JwtPayload), y el tipo genérico de respuesta de la API (ApiResponse<T>) que garantiza una estructura de respuesta coherente en todos los endpoints.

Frontend — Router y Guards

Sistema de navegación SPA con protección de rutas basada en autenticación y roles.

secure-tenis/src/router/index.ts TS ▶

Define todas las rutas de la aplicación y el sistema de guards. Las rutas están organizadas en dos grupos principales:


Rutas públicas (MainLayout): Inicio, catálogo, detalle de producto, carrito, login y registro. Las rutas de login y registro tienen el meta guestOnly: true, que redirige al inicio si el usuario ya está autenticado.


Rutas de administración (/admin): Todas protegidas con requiresAuth: true y roles ['admin', 'analista']. Las secciones más sensibles (usuarios, productos, categorías) están restringidas solo a 'admin'.


Navigation guard (beforeEach): Se ejecuta en cada cambio de ruta. Importa authStore dinámicamente la primera vez para evitar problemas de inicialización circular. Si hay token pero no hay usuario cargado, llama a fetchMe antes de evaluar el acceso. La lógica de evaluación es: si guestOnly y está autenticado → redirige al inicio; si requiresAuth y no está autenticado → redirige al login; si tiene roles requeridos y el rol del usuario no encaja → redirige al inicio.

Frontend — Stores (Pinia)

Estado global reactivo compartido entre todos los componentes y vistas.

secure-tenis/src/stores/authStore.ts TS ▶

Gestiona toda la sesión del usuario. Persiste el token en localStorage y expone las siguientes responsabilidades:


Estado reactivo: user (datos del usuario), token (JWT), loading y error.


Computed: isAuthenticated (requiere token Y usuario cargado), userRole, userName.


Métodos: login y register llaman a la API y actualizan el estado si tienen éxito. logout limpia el estado y el localStorage. fetchMe recupera el perfil del usuario desde el servidor usando el token almacenado, lo que permite restaurar la sesión al recargar la página. hasRole y hasAnyRole facilitan la comprobación de permisos en los componentes.

secure-tenis/src/stores/cartStore.ts TS ▶

Gestiona el carrito de compras como estado global, permitiendo que el Navbar muestre el contador de items al mismo tiempo que la vista CartView muestra el listado completo.


Computed: total (suma de precio × cantidad de todos los items) e itemCount (suma de cantidades, mostrado en el badge del navbar).


Métodos: load carga el carrito desde el servidor. addItem, updateItem y removeItem llaman al servicio correspondiente y recargan el carrito completo para garantizar consistencia con el servidor. clearCart vacía el carrito y limpia el estado local directamente.

Frontend — API Client

Capa de abstracción sobre fetch que centraliza la comunicación HTTP con el backend.

secure-tenis/src/services/apiClient.ts TS ▶

Wrapper centralizado sobre la API Fetch del navegador. Todos los servicios del frontend lo usan para hacer peticiones HTTP, garantizando comportamiento consistente:


getSessionId: Genera o recupera un UUID de sesión persistido en localStorage. Este ID se envía en la cabecera x-session-id en todas las peticiones, permitiendo que el backend identifique el carrito anónimo del usuario incluso sin JWT.


buildHeaders: Construye las cabeceras comunes de cada petición: Content-Type: application/json, x-session-id y, si existe, el token JWT como Authorization: Bearer <token>.


request: Realiza la petición fetch, parsea el JSON y lanza un Error con el mensaje del backend si la respuesta no es satisfactoria (código HTTP 4xx o 5xx). El objeto api exportado expone los métodos get, post, put y delete tipados con genéricos de TypeScript.

Configuración de entorno: La URL base (VITE_API_URL) se configura en .env.development (apunta a http://localhost:3000/api) y .env.production. Vite expone automáticamente las variables que empiezan por VITE_ al código del frontend.

Infraestructura — Docker Compose

Orquestación de los servicios del proyecto en contenedores aislados.

docker-compose.yml YAML ▶

Define dos servicios en red compartida:


mariadb: Imagen oficial de MariaDB 11. Crea la base de datos mydb con usuario y contraseña configurables. Persiste los datos en el volumen mariadb_data para que sobrevivan a reinicios. Implementa un healthcheck con healthcheck.sh que verifica que InnoDB esté inicializado antes de permitir que el backend arranque.


backend: Construye la imagen desde backend/Dockerfile.development. Expone el puerto 3000. Lee las variables de entorno desde backend/.env. Monta el directorio backend/ como volumen para que los cambios en el código sean inmediatos (hot-reload). Espera a que MariaDB esté sano (depends_on: condition: service_healthy) antes de arrancar.

Frontend no está en Docker: El frontend (Vite) se ejecuta directamente en el host con npm run dev. Esto permite aprovechar el Hot Module Replacement de Vite de forma más eficiente en desarrollo.

Infraestructura — Scripts de inicio

Scripts para automatizar el arranque y parada del proyecto en Windows y Linux/macOS.

start.sh / start.ps1

Script de inicio completo. Automatiza en orden: copia .env.example a .env si no existe (generando un JWT_SECRET aleatorio), instala las dependencias npm del frontend, levanta Docker Compose y opcionalmente ejecuta el seed de la base de datos (con el flag --seed / -Seed).

stop.sh / stop.ps1

Script de parada. Con el flag --clean / -Clean elimina también el volumen de datos de MariaDB. Sin el flag, solo detiene los contenedores preservando los datos para el próximo arranque.

Primer arranque: En Windows, ejecutar .\start.ps1 -Seed. En Linux/macOS, ejecutar ./start.sh --seed. El seed carga datos de ejemplo (usuarios de prueba, productos y categorías) en la base de datos, listos para usar.

Infraestructura — Prisma & Migraciones

ORM y sistema de gestión de esquema de base de datos.

backend/prisma/schema.prisma Prisma ▶

El archivo central de Prisma. Define el proveedor de base de datos (MySQL/MariaDB), todos los modelos con sus campos y tipos, las relaciones entre modelos (un User tiene muchos Order, muchos CartItem, etc.) y las enumeraciones (Role con CLIENT/ADMIN/ANALYST y LogLevel con INFO/WARNING/ERROR/DEBUG). A partir de este archivo, Prisma genera el cliente TypeScript tipado y las migraciones SQL.

backend/prisma/seed.ts TS ▶

Script de siembra de datos de ejemplo. Crea usuarios de prueba (incluyendo un administrador), categorías de zapatillas y un catálogo de productos con precios, stock e imágenes de ejemplo. Diseñado para ejecutarse una única vez durante el primer arranque del proyecto, usando upsert para ser idempotente (se puede ejecutar varias veces sin duplicar datos).

backend/prisma.config.ts TS ▶

Archivo de configuración de Prisma para el proyecto. Define la ruta del esquema y la ubicación del cliente generado, adaptado al entorno de TypeScript del proyecto.

Flujo de trabajo con Prisma: Para modificar la base de datos, se edita schema.prisma, se ejecuta npx prisma migrate dev (genera el SQL y aplica el cambio) y Prisma regenera automáticamente el cliente TypeScript tipado. Nunca se editan los archivos SQL de migración manualmente.
